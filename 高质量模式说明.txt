========================================================
高质量模式 —— 画质优先 / 显存能占则占
========================================================

【和原方案的区别】
原方案：SD1.5 + LCM 蒸馏，速度优先（12秒出图），画质天花板低
本方案：SDXL / FLUX 架构，画质优先，满步数 + 高清修复 + 二次元超分

【硬件现实】
你的 RTX 4050 只有 6GB 显存，这是物理上限。
策略：模型尽量占显存，超出部分 offload 到 16GB 内存，CPU/GPU 协同慢慢算。
实测：SDXL 立绘（含超分）约 95 秒，SDXL 动画 8 帧约 150 秒，FLUX 单帧约 2 分钟。

【装了什么】

1) SDXL 路线（主力，兼顾画质和视频）—— 已验证通过
   - Illustrious-XL v2.0 (6.46GB)：二次元立绘画质天花板，最接近你那张参考图
   - SDXL AnimateDiff (mm_sdxl_v10_beta)：SDXL 动画模块
   - SDXL VAE (fp16-fix)：颜色/细节更准
   - 4x-NMKD 二次元超分：出图后放大 4 倍到 ~5K
   实测输出：4992x7296 大图，猫耳女仆/蕾丝/眼神光/发丝都到位，画风对齐参考图

2) FLUX 路线（极致单帧，专供 sprite / TripoSG）—— 已验证通过
   - FLUX.1-dev fp8 官方版 (16GB)：单帧画质天花板，用原生 UNETLoader 加载
   - T5xxl fp8 + CLIP-L 文本编码器 + FLUX VAE (ae.safetensors)
   - 实测：1024x1024、28 步约 2 分钟；已生成猫耳女仆/黑裙褶边/托盘/挥手/纯绿背景，
     与提示词高度一致，样例见 output\flux_final_preview.jpg
   - 注意1：FLUX 偏通用/写实，二次元靠提示词描述；无成熟视频方案
   - 注意2：CFG 必须 1.0、负向提示词必须为空、用 EmptySD3LatentImage（16通道 latent）
   - 注意3：不要用 GGUF 版本！ComfyUI 0.45 与 GGUF 不兼容会输出纯噪声，
           官方日志明确建议用原生 fp8/int8 格式。GGUF 文件已弃用但仍留在目录里。
   - 注意4：之前 T5/CLIP-L 曾下到错误文件，导致图能出但完全不跟提示词；
           现已换成 comfyanonymous/flux_text_encoders 官方 SHA256 版本，
           install_hq.py 会自动校验关键文件哈希，防止再次发生。

【画风升级包】换微调底模 + IPAdapter 锁角色 + 手部修复（配置进行中）
============================================================
问题诊断：Illustrious-XL v2.0 是"未微调中性底模"，出厂偏鲜艳锐利，
靠提示词硬压柔光半厚涂是逆设定干活，画质天花板有限。三件事分开解决：

  1) 画风像不像 -> 换微调底模（出厂就是柔光软质）
     - hassakuXLIllustrious_v22：风格最贴参考图（柔和数字阴影、暖调、软边）
     - waiIllustriousSDXL_v170：最稳（肤色发质软、解剖稳、LoRA 生态大）
     - 两个都装了，用 A/B 对比选最优；同样是 SDXL 架构，6GB 能跑
  2) 手部崩 -> SDXL 架构通病，换模型只能改善，根治靠 latent 局部重绘
  3) 不像参考图那个角色 -> 换模型无用，靠 IPAdapter 喂图锁身份

新增文件（都在 D:/AI-Video-Setup/）：
  - style_workflows_api.py：base_portrait() 支持 IPAdapter 喂图；hand_inpaint() 手部局部重绘
  - verify_style.py：verify_style.py ab / ip / hand 三个测试模式
  - install_style.py：校验 WAI 官方 SHA256 + 硬链接新模型进 ComfyUI
  - ComfyUI_IPAdapter_plus 节点已装（custom_nodes），重启后生效

手部修复正确做法（重要，别再踩坑）：
  - 弃用 crop->img2img->贴回：实测有矩形接缝、发色不一致（银发画成金发）
  - 正确：make_hand_mask() 生成全图 mask（圆角矩形+羽化），
    VAEEncodeForInpaint 只对手部区域去噪，周围像素原样保留，无接缝
  - 关键：mask 的 box 必须按每张图手部实际位置指定，不能写死
  - 用法：verify_style.py hand（会自动从 output 找底图；也可自己传 box）

IPAdapter 用法：
  - 参考图放到 ComfyUI\input\，base_portrait(ref_image='xxx.png', ip_weight=0.6)
  - ip_weight 0.5-0.7 锁身份又保留提示词；过高会连构图一起锁死

【画风升级包 · 验证结果】
============================================================
A/B 对比（同提示词、同 seed、832x1088、32 步、CFG 4.5、euler）：
  - WAI v17：38 秒，画风最接近参考图（柔光暖灰、半厚涂、奶油肌），眼睛干净通透
  - Hassaku v2.2：30 秒，偏亮偏清透，虹膜高光偏碎，画风略艳
  => 结论：选 WAI v17 作主力底模。都比原 Illustrious-XL 强一个档次。

IPAdapter 锁角色（参考图 = 用户原图）：
  - weight 0.6：保留比 V 手势和全身构图，红眼/心形泪痣/红白配色/柔光画风都锁住
  - weight 0.9：锁得更紧，但构图被拉成参考图那种暗背景特写，丢了手势
  => 结论：0.6 最平衡，0.9 只适合"要极像原图、不在乎构图"的场景

手部局部重绘（最终可用方案）：
  - 弃用 VAEEncodeForInpaint：它会用灰色填充 mask 区域，denoise 不足时残留灰块+生成无关图案（实测生成过一块灰底兔子图标）
  - 正确：VAEEncode（完整编码原图）+ SetLatentNoiseMask（只给 mask 区域加噪）+ KSampler denoise 0.55
  - 效果：手部结构从模糊变清晰，无接缝、无灰块，衣服背景完全保留
  - mask 由 make_hand_mask 生成（圆角矩形 + 高斯羽化），box 必须按实际图手部位置指定

重要坑（务必记住）：
  1) IP-Adapter 模型要和 CLIP Vision 匹配：
     - ip-adapter_sdxl.safetensors 是 ViT-bigG（proj 1280 维）
     - ip-adapter_sdxl_vit-h.safetensors 才是 ViT-H（proj 1024 维）
     - 配 clip_vision_h（ViT-H）必须用 vit-h 版本，否则报 size mismatch
  2) 负向词加 "hair ornament" 反而会诱发蝴蝶结发饰，别加
  3) 加 "symmetrical face" 会引发奇怪构图，别加
  4) 换 seed 会完全换构图，稳定出图要固定 seed

一键成品命令：
   cd /d D:/AI-Video-Setup
   "D:/ComfyUI/ComfyUI_windows_portable/python_embeded/python.exe" verify_style.py final
   （WAI + IPAdapter 0.6 + 手部重绘，约 70 秒）
   其他模式：ab（A/B 对比）/ ip（锁角色两权重）/ hand（只修手）

样例：D:/AI-Video-Setup/output/final_style_wai.jpg

【分步作画流水线】用时间换有效分辨率（实验报告）
============================================================
设计目标：模仿真人画师"先骨架→草线→分部位→光影→背景"的流程，
牺牲时间、合理分配显存，让 6GB 卡产出更高细节。

核心结论（实验得出，不是推测）：
  **扩散模型的每一步采样都是"重新想象整张图"，不是"在画布上添笔"。**
  所以分步的成败不在分几步，而在每一步怎么锁住上一步的成果。
  凡是"重新采样"的地方，都会破坏已有细节；能不用模型就不用模型。

实验设计（同一 seed、同构图、同超分、同部位精修，只改收尾方式）：
  A 部位精修后不收尾          -> 发丝分层清晰、高光精致、腮红线细密
  B 用模型低强度重绘 denoise 0.25 -> 明显抹平：发丝变糊、高光成白团、腮红线消失、
                                     连眼睛位置和眉形都变了（构图被重新想象）
  C 纯像素调色收尾            -> 几乎完整保住 A 的细节，只调色温与对比
  => 结论：收尾必须用纯调色（PIL），绝不能用模型重绘。B 比 C 多花 118 秒还更差。

流水线四阶段（painter_pipeline.py 已实现并跑通）：
  1 构图   640x832 / 24 步，只求姿势和布局对                 约 26 秒
  2 超分   4x-NMKD 纯像素放大，不重采样，结构完全保留          约 10 秒
          2560x3328 再缩到 1664x2163（控制后续处理开销）
  3 部位   把脸/手裁出 -> 放大到 1024 长边 -> 单独重绘 -> 羽化贴回
          face 840x1024 denoise 0.42   约 30 秒
          hand 787x1023 denoise 0.42   约 22 秒
  4 收尾   纯调色（降饱和 0.94、微提亮、微对比）               约 0.5 秒
  合计约 1 分 31 秒（模型重绘收尾版要 3 分 16 秒且质量更差）

为什么这样能提升质量（机制）：
  一次性出 832x1088，脸只占约 200px；分步把脸单独裁出画到 1024px 再缩回，
  等于让模型把全部注意力放在这块。这是"有效分辨率"的提升，不是超分能替代的
  —— 超分只放大已有像素，分部位是真让模型重画这块。

已暴露的真实短板（诚实记录）：
  1) 部位框是按比例手填的，没有人体检测器。换构图就必须重新标 box。
     => 想自动化要装检测模型（YOLO/MediaPipe），6GB 能跑但再加几百 MB。
  2) 部位重绘会在贴回边界产生轻微色调差，羽化能掩盖但放大看仍有痕。
  3) 构图阶段没有骨架控制，姿势和造型是随机的。
     => 要真正实现"先想骨架"，必须装 ControlNet（OpenPose/Canny/Depth/Lineart）。
        当前 controlnet 目录是空的，需下载 SDXL 版，每个约 2.5GB，三个约 7.5GB。
  4) 分部位各画各的光，全局光影一致性靠人调，没有物理约束。

能做到 / 做不到（不要自欺）：
  能  ：局部细节精度（脸、眼、手可以远超一次性出图）、结构可验收可回退、
        6GB 出 1664x2163 级细节（任何时刻显存只放一块工作集）
  不能：模型知识容量（不懂的东西分步也不会懂）、全局光影物理一致性、
        一次成型的整体感（容易拼贴感）、"与大模型对齐"这个说法本身不成立
        更准确的说法是"用时间换有效分辨率"，不是"对齐大模型"

用法：
  cd /d D:/AI-Video-Setup
  set PY=D:/ComfyUI/ComfyUI_windows_portable/python_embeded/python.exe
  %PY% painter_pipeline.py run                     完整流程（纯调色收尾）
  %PY% painter_pipeline.py run --parts face        只精修脸
  %PY% painter_pipeline.py run --parts none        对照组（只构图+超分）
  %PY% painter_pipeline.py run --light-denoise 0.25  对照实验（模型重绘收尾，负收益）
  %PY% painter_pipeline.py run --part-denoise 0.5  部位重绘更狠（风险：改结构）
  输出：ComfyUI\output\painter_*\ 各阶段，最终图在 ComfyUI\input\painter_*_final.png

  compose_size  640x832 出半身；再小会丢结构，再大构图阶段就慢了
  target_w      1664 是质量/耗时平衡点；2048 更细但部位重绘耗时会翻倍

============================================================
【结构层注入】骨架 / 线稿 / 分层时序（实测报告）
============================================================
目标：把"先想骨架→再补草线→后上质感"真正落进模型的去噪过程，
而不是在模型外面套流程。

★ 最重要的认知修正（务必记住）：
  火柴人骨架（OpenPose / COCO 18 点）**不包含手指信息**。
  它的手部只有"腕关节"一个点，手指完全不在条件里。
  所以"靠骨架避免六指"这个预期不成立 —— 条件里根本没有手指信息，
  模型仍然只能靠统计先验去猜，猜错就是六指或畸形。
  分工应该是：
      骨架 OpenPose  -> 管姿势、比例、朝向（不含手指）
      线稿 Scribble  -> 管轮廓、衣褶、**手指数量**（想五根就画五根）

★ 三个对照实验（同一套软硬件，SDXL + ControlNet）

  实验1  骨架 → 全身（768x1152，28步，60.6 秒）
    输入：程序生成的火柴人（双臂上举）
    结果：右手确实举起来了，姿势跟随成功。
          但构图从全身变成了半身特写，腿消失。
    原因：a) 骨架只有棍子，模型不知道画面边界该多大
          b) profile 提示词里有 "upper body"，直接把构图拉成半身
    结论：骨架能控姿势，但提示词和骨架会打架，必须同时约束构图。

  实验2  线稿 → 白底生成单手（768x768，26步，42/34 秒）
    输入：程序画的"五指张开""五根 V 手势"线稿
    结果：手指数量完全正确（五指→五指，V→V），形状也跟随。
          但画风崩成 3D 塑料手 / 人体模型手，完全不是二次元。
    原因：白底凭空生成丢掉了上下文（肤色、光照、画风先验），
          ControlNet 线稿强度 0.8 直接主导了生成。
    结论：线稿能控手指数量，但**不能脱离上下文单独用**。

  实验3  原图 crop + 线稿 + img2img（640x1024，30步 denoise 0.55，44.2 秒）
    输入：从已生成的成品里裁出手部区域 + 五指 V 线稿
    结果：**画风完整保住**（二次元柔光、肤色光照项圈衣领全部一致），
          手势被成功改成 V，五指结构清晰无六指。
    结论：这就是可行的解 —— 上下文给画风，线稿给结构，img2img 负责融合。

★ 分层时序（"调思考步骤"的工程形式）
  扩散模型没有"思考"，但它有"早期步定大局、后期步补细节"的隐式规律。
  把这个规律显式化，就是给不同结构条件分配不同的生效步数区间
  —— 也就是 ControlNet 的 start_percent / end_percent：

      骨架 OpenPose   0%  ~ 45%   strength 1.0   钉死姿势与比例
      线稿 Scribble  15%  ~ 70%   strength 0.8   叠轮廓 / 衣褶 / 手指数量
      剩余 30% 步数    无约束                      放开补光影质感

  实测这套叠加能正常工作（实验1 的右手上举就是骨架层在 0-45% 起的作用）。

★ 能做到 / 目前做不到
  能做：姿势可控、手指数量可控、画风不被结构条件破坏（实验3）
  做不到（当前 6GB + SDXL 生态）：
    - 训练一个"骨架直接编码进潜空间"的适配器（需 24GB 级训练显存）
    - 自回归式笔触生成（真科研，非编排问题）
    - 全自动部位定位（需 DWPose / MediaPipe 检测模型，尚未安装）

★ 新增文件与用法
  skeleton_gen.py   程序化生成骨架和手部线稿（手指数量可指定）
     python skeleton_gen.py pose --preset v_sign --out pose.png
     python skeleton_gen.py hand --fingers 5 --style v --size 640x1024 --out hand.png
  struct_paint.py   分层注入引擎（骨架/线稿/init/denoise 全参数化）
     python struct_paint.py pose --pose pose.png --size 768x1152
     python struct_paint.py hand --init crop.png --sketch hand.png --denoise 0.55
  ControlNet 模型（已装，diffusers 格式 ComfyUI 可直接读）
     controlnet_openpose_sdxl.safetensors   2.33GB
     controlnet_scribble_sdxl.safetensors   2.33GB
     来源 xinsir/*-sdxl-1.0（hf-mirror），各自 844 tensors

★ 调参经验
  pose_end      0.45 是分水岭；调高到 0.7+ 会让画面变成"贴图感"的僵直姿势
  sketch_end    0.70 合适；0.9+ 会让线稿的粗线条直接印在成品上
  sketch_strength 0.85 能改手势，1.0+ 会改掉整只手的姿态
  denoise       img2img 时 0.5-0.6 能改手势又保画风；0.7+ 会丢原图肤色光照

============================================================
【自动提骨架实测 + 自训练可行性】图->骨架->画面
============================================================
用户设想：让模型能"根据图例自动脑补骨架"，再"先浮现骨骼定位，后浮现画面盖住骨骼"。
拆成两件独立的事，能力要求完全不同：
  感知：图 -> 骨架（pose estimation，现成模型可做，但二次元精度不足）
  生成：骨架 -> 画面（ControlNet 已解决，见上一章）

★ 实测：现成 rtmw/DWPose 在二次元图上提骨架（rtmlib，onnxruntime CPU）
  环境：onnxruntime 1.32 + opencv 5.1 装在 ComfyUI 的 Python 3.12 里（不污染 torch）
         rtmlib 从 codeload 下 zip 解压到 D:/AI-Video-Setup/rtmlib_src，无需安装
  模型：yolox_m (203MB) + rtmw-dw-x-l 256x192，自动下到 ~/.cache/rtmlib
  测试图：本人 3DCG 风格生成图（832x1216）

  结果：persons 1 | body pts>0.3: 17/17 | hand pts>0.3: 22/42 | mean score 0.761
  观察：
    - 检出率很高，面部关键点（眼鼻嘴）密集且准确
    - 但**骨架整体偏移**：肩线画到了脖子处，髋线抬到了腰部以上
    - 下肢严重失真（裙子遮挡，模型按真人比例猜）
    - 手部只检出 22/42 点（相当于只识别出一只手）
  结论：**能检出，但精度不足以直接用于"重建同姿势"**。
        原因是这些模型全部用真人数据训练，二次元头身比、遮挡、手部画法都不同。
  => 这恰好证明：要在二次元上可靠提骨架，**确实需要自己训练/微调**。

★ 关键判断：要训的不是 SDXL，是一个小骨架预测器
  训练 SDXL 需要 24GB+ 显存，6GB 不可能。
  但"文本/图 -> 骨架热图"是一个小模型任务：
    输入 512x512 图（或文本 embedding）-> 输出 64x64x17 热图
    模型规模 5-15M 参数（轻量 UNet / ResNet）
    6GB 显存可跑 batch 4-8 @ 512，几小时能出结果
  **这是整套构想里唯一能在你机器上真正"训练"出来的东西。**

★ 自训练的闭环（可行）
  1 用现成 rtmw 对大量二次元图自动打骨架（弱标签，快但会错）
  2 人工挑一部分修正明显错位（可选，几十张就够纠偏）
  3 在弱标签 + 修正样本上微调小预测器
  4 预测器出骨架 -> ControlNet -> 画面
  这本质是 pseudo-labeling / self-training，方法成熟，工程可行。

★ "先浮现骨骼、后浮现画面"的三种实现层次
  层1 两阶段串联（推荐，现在就能做）
      预测器/人工骨架 -> ControlNet -> 主模型生成
      是"先骨骼后画面"，但骨骼来自外部，不是同一网络内部
  层2 条件时序（已做）
      骨架 0-45% 强约束 -> 线稿 15-70% -> 后 30% 放开补质感
  层3 同一网络内部两阶段（真科研）
      在 latent 里加结构通道，或改架构让模型自己先输出骨架
      需要重训大模型，6GB 不现实

★ 新增文件
  extract_pose.py      从任意图片提取骨架（rtmlib/rtmw，含手部关键点）
     python extract_pose.py 输入图.png 输出图.png
     依赖已装在 ComfyUI 的 Python：onnxruntime 1.32、opencv 5.1

★ 落地建议顺序
  1 先补"人体框自动定位"（用 rtmw 的检测框替代手填 box，painter_pipeline 的部位框可自动化）
  2 收集 2000-5000 张二次元图，用 rtmw 自动打标
  3 训小骨架预测器（6GB 可跑）
  4 接入 struct_paint.py 的骨架输入，形成完整闭环

============================================================
【自进化调参器】一张张出图 -> 反馈 -> 自动逼近你的偏好
============================================================
★ 先划清能做和不能做的界线
  ✗ 不能让 SDXL 边跑边改权重（在线学习）。
    扩散模型没有"单样本在线更新"这回事；一帧一帧喂图学不到东西，
    真要改权重必须离线训练，6GB 也扛不住，还会灾难性遗忘。
  ✓ 能做的是**参数搜索**：把 CFG / 步数 / denoise / IPAdapter 权重当成可进化的基因，
    每出一张图给一个评分，用退火爬山逐步逼近你的偏好。
    这才是"自己调参数"的正确形态，而且真正有用。

★ 已实现：auto_tune.py
  搜索算法：退火爬山
    前期（前 3-6 轮）纯随机探索，保证覆盖参数空间
    后期在当前最优附近做高斯扰动，扰动幅度随迭代衰减
    历史累积到 profiles/tuning/<画风>.json，下次接着跑，越用越准

  两种反馈方式
    --auto    自动评分：锐度(拉普拉斯方差) + 对比度 + 色彩丰富度 + 崩坏惩罚
              有 --ref 时再混入与参考图的结构/色彩相似度
    （默认）  交互模式：每轮出 3 张，你选最喜欢的一张，系统据此更新方向
              这是最准的，也最接近"一张张喂图"的字面意思

  写回：--apply 把历史最优参数写进画风档，自动生成 .bak 备份

★ 实测（soft 画风，5 轮，约 2 分钟）
  cfg 6.204 / 37步 -> 0.807   （过曝，背景发亮）
  cfg 4.529 / 25步 -> 0.791   （**手部崩坏**，评分最低 —— 抓到了）
  cfg 3.554 / 30步 -> 0.827
  cfg 4.984 / 31步 -> 0.830   ← 最优，手部清晰、构图完整
  cfg 5.328 / 34步 -> 0.818
  最优 cfg4.98/31步 很接近此前人工调的 4.5/32，说明指标方向是对的。

★ 诚实说清局限
  1 自动评分是**代理指标**，会被"过锐、过饱和"骗。这次它碰巧抓对了
    （0.791 那张手确实崩了），但 0.79~0.83 这个区间内的排序不一定可靠。
  2 区分度不高：0.04 的分差对应着明显的质量差异。想要精细偏好，用交互模式。
  3 参数空间现在只有 2-3 维。往里加提示词、采样器、ControlNet 强度会让
    搜索成本指数上升（每轮 25-50 秒），不建议一次超过 4 维。

★ 用法
  cd /d D:/AI-Video-Setup
  set PY=D:/ComfyUI/ComfyUI_windows_portable/python_embeded/python.exe
  %PY% auto_tune.py --profile soft --trials 9 --auto       自动跑 9 轮
  %PY% auto_tune.py --profile soft --trials 6              交互选图（推荐）
  %PY% auto_tune.py --profile 3dcg --ref 目标.jpg --auto   加相似度约束
  %PY% auto_tune.py --profile soft --apply                 写回最优参数
  %PY% auto_tune.py --profile soft --reset                 清空历史重来
  产物：ComfyUI\output\tune\*.png，历史 profiles\tuning\soft.json

★ 为什么不做"真·自进化"
  真正的在线学习要求：可微的反馈信号 + 每步更新权重。
  扩散模型的生成过程不可反向传播到"我的审美"，只能靠外部打分做黑盒搜索。
  LoRA 增量训练理论上可以当"学习"，但每张图训一次是分钟级，
  且十几次就会灾难性遗忘 —— 得不偿失。
  参数搜索是这条路里性价比最高的形态：不碰权重，几分钟就能收敛。

问题一：界面里报 "Required input is missing: vae"
----------------------------------------

  [ERROR] * VAEDecode 9:
  [ERROR]   - Required input is missing: vae

  inputs 写成了旧版列表格式 [["model","MODEL",8], ...]，
  现在的界面只认 {"name":..,"type":..,"link":..} 对象格式，
  结果所有连线在界面里都是断的。

修复：
  - 新写 export_ui.py，用"API 语义图 -> UI 图"自动转换，
    link id 全部自动分配，控件值按 WIDGET_ORDER 排序，
    输入口按 ComfyUI 节点定义排（错序会把线挂到别的槽）
  - 03 / 04 / 06 用 export_ui.py 从 hq_workflows_api.py 重建
  - 02 的重复 link 拆成 12 / 14 两条
  - 新写 check_workflows.py 做体检，三类致命错误全查：
      1 输入口引用不存在的 link（断线）
      2 link 的目标节点/槽位与引用方对不上（错线）
      3 多条 link 抢同一个目标口
  - 5_画风切换.bat 菜单加了 w = 查工作流

体检结果：6 个工作流全部 [好]。
回读比对：03/04/06 从界面图反解回 API 图，与原始 API 图完全一致。

问题二：出图是彩色噪点 / 霓虹条纹
----------------------------------------
根因：AnimateDiff 运动模块需要 16 帧以上的时序上下文。
  帧数被改小就当场崩，而且不是报错，是"成功地"输出垃圾：
      1 帧  -> 纯彩色噪点（一点结构都没有）
      8 帧  -> 霓虹条纹怪图（人物轮廓还在，但线条炸开）
      16 帧 -> 正常
  实测对照（512x512 / MeinaV7 / LCM）：

============================================================
【故障复盘2】"切换画风没反应" —— .bat 是 LF 换行
============================================================
现象：双击 5_画风切换.bat，菜单出来了，但输入编号后什么都没发生，
      黑窗口里还会闪过 "xxx 不是内部或外部命令"。

根因：这些 .bat 被写成了 LF（Unix）换行。
  Windows 的 cmd 解析批处理时按 CRLF 断行，遇到纯 LF 会把
  上一行和下一行粘在一起、或在语句中间断开，
  于是 echo / set / if 这些命令被打散成碎片去执行 ——
  菜单里能显示的那几行是碰巧没被拆坏的。

实测证据（转 CRLF 前）：
  1_启动ComfyUI.bat        CRLF=0  裸LF=9
  2_启动ComfyUI_省显存.bat   CRLF=0  裸LF=9
  3_打包精灵图.bat          CRLF=0  裸LF=9
  4_启动_高画质模式.bat       CRLF=0  裸LF=12
  5_画风切换.bat            CRLF=0  裸LF=105
转成 CRLF 后同样的菜单：0 条命令报错，编号能正常切换。

修复：全部 .bat 重写为 CRLF + UTF-8 无 BOM（保留 chcp 65001）。
  6_一键精灵图.bat 一开始就是 CRLF，所以它一直是好的 ——
  这也是为什么"一键精灵图能用、切画风不能用"。

自查办法（以后再怀疑 bat 坏了）：
  python -c "d=open(r'D:/AI-Video-Setup/5_画风切换.bat','rb').read(); print('CRLF',d.count(b'\r\n'),'裸LF',d.count(b'\n')-d.count(b'\r\n'))"
  裸 LF 应该是 0。

经验：写 Windows 批处理必须 CRLF。
  用 git 提交时也要注意 core.autocrlf，否则下次 pull 又变回 LF。

【故障复盘3】.bat 用 UTF-8 + chcp 65001 会解析错行
============================================================
现象：7_准备训练集.bat 里这行被从中间截断，

      "不是内部或外部命令" 且中文正常显示。

以后新增 bat，两条底线：
  1 CRLF 换行（裸 LF 会拆命令）

【质感能不能单独驯成一个小 LoRA】

  普通 LoRA 学的是"整张图"，包括角色、服装、构图。
  只学质感的关键不是数据集，而是 **block_dims 只开中间块和上层块**：

  这样构图留给提示词，LoRA 只接管渲染质感。
  数据要求反直觉：要"同一套质感、不同角色/服装/场景"，
  否则会连带把角色学进去。步数也少，600-1000 步就够。

C 成对数据训「细节增强器」
  拿原图程序生成降质版（模糊/降采样/加噪），把成对样本当差分学。
  这就是 Detail Tweaker 的原理。效果最纯，工程最重，以后再碰。

【质感流水线】texture_pipeline.py
============================================================
三段串起来，各管一段：
  1 出图（叠细节 LoRA，可选）
  2 4x 超分（4x-NMKD，把已有的高频还原出来，不是无中生有）

============================================================
【分层作画：能拆到什么程度】layer_paint.py
============================================================
先纠正一个前提：画师的层是因果链（每层依赖上一层），
扩散模型的层是并行的 —— 一次去噪同时决定结构、明暗、材质。
所以不能真的"先铺固有色再二分"，只能把每层变成一次独立图像操作，
靠遮罩和约束把层串起来。

拆成「空间 × 工序」五层，已实现并实测：
  L1 结构层   提示词 + 可选骨架/线稿 ControlNet 定构图      33s
  L2 脸部层   rtmw 自动框脸 -> 局部重绘眼睛/睫毛/皮肤        30s
  L3 手部层   rtmw 自动找手 -> 局部重绘手指（找不到就跳过）  28s x2
  L4 超分层   4x 超分，还原已有高频                          18s
  L5 光效层   高光提亮 + 局部对比 + 锐化（纯 PIL）            9s
  合计约 2 分 24 秒 / 张，输出 3328x4864，另出五联对比条。

实测改动量（同一 seed，832x1216）：
  L1->L2 脸部区  平均差 5.17/255，20.8% 像素有明显改动
  L2->L3 手部区  平均差 3.15/255，10.4% 像素有明显改动
  L1->L3 整体    30.2% 像素有改动
  结论：结构上确实在动，但视觉上"台阶感"主要来自 L4 和 L5。

哪些层模型做得好、哪些做不好（重要）：
  做得好  线稿约束、大色块定调、部位局部精修、超分、调色
  做不好  二分（明确光影分界）、金属/反光刻画、暗部加深
  原因：金属和反光需要材质理解，模型只会画出"看起来像金属的图案"，
        而且重绘会改形状 —— 所以金属别让模型画，交给后期叠色更稳。
  暗部加深更危险，容易脏、容易糊。

层数不是越多越好：
  每加一层都是重新采样，层间必然漂移（同 seed 也会变），
  5 层已经是收益/风险的分水岭。真想再细，优先加"眼睛单独一层"
  （denoise 0.55 + 只框眼睛），这是画师流程里第 5 步，
  也是唯一明显能提质的部位层。

【分层实测结论】哪层有用、哪层会坏事（有对比图）
============================================================
做完三组 100% 局部对比，结论比预想的更尖锐：

1 超分 + 光效（L4 + L5）—— 唯一稳定提质
   发丝一根根分出来、皮肤纹理变细、高光更亮，没有白边。
   这是纯像素运算 + 超分模型，不重新"猜"内容，所以不会跑偏。

2 脸部全框重绘（L2）—— 会改表情，别默认开
   实测两次：
     通用提示词（detailed eyes + catchlight）+ denoise 0.38
       -> 半闭睡眼被改成睁眼 + 青色虹膜，眼神完全变了一个人
     保表情提示词（keep the same expression, same eye shape）+ denoise 0.30
       -> 还是睁开了
   原因：不是提示词没写对，是**粒度太粗**。框住整张脸时，
         "脸 + 精致眼睛"这个语义先验会把眼睛强行打开。
   改法：把脸层默认关掉（要开加 --face），真要刻画眼睛，
         必须把 mask 收紧到眼周，并在提示词里写明当前表情。

3 手部自动检测（L3）—— 在二次元图上不可信
   rtmw 把手框到了脚上（box 落在画面下部），
   结果"手部重绘"实际重画的是鞋和袜口。改动量 10.4% 全是脚。
   改法：默认关掉自动模式，改成 --hand-box x0,y0,x1,y1 手动框。

所以现在的默认流水线是：
   L1 出图 -> L4 超分 -> L5 光效        约 60 秒/张，稳定收益
   --face / --hand-box 需要时才开，开之前先想清楚会改什么

一句话：模型擅长"在已有内容上加细节"，不擅长"局部重画还保持原样"。
所以凡是"重绘"的层，粒度必须窄到只包住目标，否则它会顺手把周围的语义一起重写。

【分步提示词】每层一句提示词，能拆，但拆法不是你想的那样

一 为什么"每层换一套提示词"会翻车
----------------------------------------
提示词对画面的控制力，取决于 denoise：
   denoise 0.30   原图信息占 70%，模型只是微调，你写 detailed eyes
                  它也只会在原眼形上蹭一点 —— 提示词基本无效
   denoise 0.60   提示词才真正接管，但它会顺手把表情、脸型、服装一起改掉
   denoise 1.00   完全按提示词重画

所以"分层提示词"能不能生效，靠的不是提示词本身，
而是 denoise × mask 粒度 × 提示词 三者的配套。
只拆提示词、不调 denoise，等于白写。

二 正确拆法：主体固定，每层只追加职责词
----------------------------------------
   base   = "1girl, pink hair, white sailor uniform, half-closed eyes, ..."
            （全程不变，锚住"画的是谁、什么姿势"）
   S1 粗图 = base + "3d, cgi, smooth shading, low detail, painterly base"
   S2 细化 = base + "highly detailed, fine texture, hair strands, pores"
   S3 眼周 = base + "same half-closed eyes, keep the same eyelids, ..."
   S4 边缘 = 纯算法 USM（不给模型）
   S5 滤镜 = 纯 PIL 调色（不给模型）

如果你每层都换一整句主体描述（比如 L1 写"粉色短发少女"、
眼层写"精致的眼睛"），模型会当成画另一个东西，语义必然漂移。
实测过的旧案例：脸部层写 detailed eyes + catchlight，
结果把半闭睡眼改成了睁眼 + 青色虹膜，眼神完全换了个人。

三 实测对照（同一张粗图，512x832，同 seed）
----------------------------------------
   A  粗图 18步 -> 4x 超分 -> 调色          20.1s  2048x3328
   B  A 的基础上加 latent x1.5 细化 dn0.50  24.1s  3072x4992
   C  B 的基础上加眼周层 dn0.32             22.1s  3072x4992

   脸部锐度（rtmw 脸框归一化到 420x420 后算拉普拉斯方差，同一把尺子）
      A  512 粗图 + 超分          61
      B  512 粗图 + 细化 + 超分   108     (+77% vs A)
      C  B + 眼周                 121     (+12% vs B)
      参照：768x1344 直接一次出图 + 超分   96

   **这张参照值很重要，它把上面的 +77% 打回原形：**
   B 比单次高分辨率出图只多 12%，也就是说"细化层"的收益，
   大部分是在补回"512 粗图丢掉的东西"，不是真的比一次出图更强。
   时间上 B 约 70s（20+24+超分16+调色），单次出图约 59s。
   -> 分层细化的性价比是 +11 秒换 +12% 锐度，还要承担伪影风险（见第六节）。
      它真正的价值不在画质，在工作流：512 粗图 20 秒就能试构图，
      满意了再花 24 秒细化，试错成本比直接跑 768 低一半。

   目视差异：
      A  头发糊成块、皮肤像塑料、眼睛是一块发光的蓝色片、
         裙褶边缘发软、手是一团糊的棕色块
      B  发丝一根根分开、皮肤有微弱毛孔与明暗结构、
         眼睑结构清晰、裙褶分离、手指轮廓能数出来
      C  和 B 肉眼几乎看不出差别（锐度 +12% 是眼周边缘对比变强，
         不是细节变多，属于"假锐度"）

   结论：整套拆分里真正干活的是 S2 细化层，别的都是配角。

四 眼周层的两次失败（重要）
----------------------------------------
第一次 denoise 0.42 + "heavy eyelids, sleepy"：
   眼周被重采样成青黑暗沉，眼白几乎消失，像严重黑眼圈。
   原因：小区域重新采样时噪声比信号多，暗部会被无中生有地加深。
第二次 denoise 0.32 + 负向压 dark circles/bruised under-eye：
   眼周干净了，但锐度只从 110 涨到 114，几乎白做。
   -> 眼周层目前的定位是「安全但基本无用」，
      想真正刻画瞳孔高光，得配 ControlNet 锁住眼形，那是另一套。

五 你那个比喻，落到模型上的对应关系
----------------------------------------
   描色（定构图线稿）   -> ControlNet scribble/pose + denoise 1.0
   填色（大色块）       -> 粗图层 denoise 1.0，提示词只写大词
   局部 P 图            -> 部位窄 mask + denoise 0.35-0.5 + 该层提示词
   边缘强化             -> 纯算法（USM），千万别给模型：
                           模型做边缘只会画出脏边和 halo
   全局滤镜             -> 纯 PIL 调色，全图重绘一次就掉一次细节
                           （实测：全图 dn0.3 统一光影，多花 118 秒且更差）

六 细化层的副作用（诚实记录）
----------------------------------------
denoise 0.5 的细化是"无差别加高频"，它不会判断哪里该加：
   - 袜口无中生有出一小块黑色异物（A 组没有）
   - 裙摆下缘被超分成锯齿状白边
   - 头顶一度冒出白色对话气泡（负向补 speech bubble/thought bubble 后消失）
想抑制，两条路：给细化也套 mask（只细化人物不细化背景），
或者细化后加一道"异物清理"（检测孤立小块）。目前都没做。

七 时间账
----------------------------------------
   粗图 20s + 细化 24s + 超分 16s + 调色 9s          = 69s 出 3072x4992
   768x1344 直接一次出图 32s + 超分 18s + 调色 9s    = 59s 出 3072x5376

   -> 拆分的代价 +10s，换 +12% 锐度，还要承担伪影风险。
      单看画质，不划算；看试错成本才划算：
      512 粗图 20 秒就能看构图，不满意直接重摇，
      这比每次跑 59 秒再发现姿势不对要省得多。

一 为什么所有重绘都会把半闭眼改成睁眼
----------------------------------------
试了三版，全部失败，且失败方式一模一样：

  版本           做法                          结果
  v0 整脸框      dn0.42 整张脸重绘             睁眼 + 青虹膜，变了个人
  v0 眼带        脸框上 20~52% 横带            同上
  v1 线稿锁      Canny 线稿 + scribble CN      仍是睁眼，还多了个黄色斑块
  v2 ROI 3x      裁 ROI 放大 3 倍再修          仍是睁眼
  v2 ROI 1024    ROI 拉到 1024 宽 + CFG 7.0    仍是睁眼

  根因不是参数，是两条硬约束：
  1 像素不够：768x1248 全身图里眼睛只有 45x21 像素，
    换算到 latent 是 5.6 x 2.6 格。2.6 格的高度里，
    模型只能决定"这块是亮的还是暗的"，画不出瞳孔和睫毛。
  2 先验太强：Illustrious 系底模训练数据里，眼睛绝大多数是睁开的。
    只要这块区域被重新采样，模型就按先验画开。
    mask 收紧、CFG 提到 7、负向写 wide open eyes，全都压不住。

  所以"重绘眼部"这条路，在 6GB / 全身构图 / 这个底模 的组合下是死路。
  想真做，只有两条：出半身或胸像（眼睛有 100+ 像素），
  或者训一个眼部 LoRA。

二 有效的做法：纯算法增强，不重绘
----------------------------------------
  做法（眼睛在画面里占比小时唯一安全的加固）：
    1 rtmw 定位双眼
    2 取含双眼的 ROI
    3 ROI 内：LAB 的 L 通道 CLAHE(clip 1.6) + USM(0.55, radius 1.0)
    4 用**径向渐变** alpha 贴回（不能用矩形羽化，会留可见的方块接缝）
    耗时约 10 秒，形状 100% 不变

  效果：眼裂、睫毛、眼影、鼻梁高光都更清楚，表情完全保留。
  代价：皮肤会略粗，所以增益要压在 clip 1.6 / USM 0.55 以内，
        超过这个数皮肤就开始起颗粒。

  一条踩过的坑：第一版用矩形羽化贴回，ROI 边界出现一条直线接缝，
  因为 CLAHE 的增益在边界处不连续。改成径向渐变就没了。

【朴素模式对照】你的判断是对的：不追求华丽时，分步不占优
============================================================
同一 seed 20261119，同一底模，只改提示词华丽度：

  模式            单次 768 一次出图   512粗图+细化
  华丽词          96                  108       分步 +12%
  朴素词          165                 92        分步 -44%

  华丽词 = 带 masterpiece / absurdres / highly detailed / octane render /
           subsurface scattering / cinematic lighting
  朴素词 = 只写"是什么"：full body, pink hair, white sailor uniform, plain wall

  为什么反转：
  分步细化的全部价值，来自"细化层的提示词能推动模型加东西"
  （highly detailed / fine texture / hair strands）。
  朴素模式下两层提示词几乎一样，细化层无事可做 ——
  它只剩下"latent 1.5x 上采样再用 denoise 0.5 重采样一次"，
  而上采样本身是插值、会软化，于是净亏。

  另一个反直觉的点：朴素单次锐度 165 比华丽单次 96 高得多，
  但朴素那张并不更好看 —— 华丽词让画面变柔、有景深、皮肤通透，
  锐度低是"氛围"的代价。所以锐度只能做同条件对照，
  不能拿来跨风格比高低。

  结论：
    要华丽质感的图 -> 分步，能多榨 12%
    要素净/干净的图 -> 单次出图，别分步
    这也意味着分步不是通用优化，它是"提示词能表达出增量"时才成立的技巧。

【四层拆解方案】背景 / 特效 / 动作 / 质感
============================================================
先说结论：这四层的成熟度差别极大，不能一起上。

  动作层    成熟。skeleton_gen.py 生成火柴人（含每根手指的三段关节）
            -> openpose ControlNet，用 start/end percent 控制生效区间。
            struct_paint.py 已实现并做过三组对照：
            骨架在前 45% 生效定姿势，之后放开让模型补细节。
            这是四层里唯一"真的能按你的意思动"的一层。

  质感层    成熟。4x 超分 + LAB 调色，稳定收益，已进 texture_pipeline / fullbody。

  特效层    半成熟。靠 mask 局部重绘只能做"贴上去的光"，模型不会理解
            "魔法阵要跟手一起动"。可行的做法是：
            mask 框在人物周围 -> 提示词换成 magic circle / glowing particles
            -> denoise 0.45。能出效果，但形状随机，每次不一样。
            要做真特效，得走合成（PNG 素材叠层），不是提示词能解决的。

  背景层    不成熟，卡在前置件缺失。
            要单独换背景，必须先有"人物分割 mask"，
            而这台机器没装分割模型（rembg / u2net，约 176MB）。
            用 rtmw 的 17 个身体点拼多边形只能得到很粗的轮廓，
            边缘会把人抠出锯齿，比不换还难看。

  所以现实的推进顺序是：动作层 -> 质感层（都现成）
                        -> 装 rembg 打通背景层
                        -> 特效层最后做，且用素材合成而非重绘

  四层和已有技术的对应关系：
      动作层   skeleton_gen.py（生成）/ extract_pose.py（提取）/ struct_paint.py（注入）
      质感层   texture_pipeline.py / fullbody.py 的 4x + 调色
      背景层   [缺] 分割模型 -> 反相 mask -> 只重绘背景
      特效层   [缺] PNG 素材 + alpha 合成，或局部重绘碰运气

一 为什么不用 rembg
----------------------------------------
pip install rembg 卡了 9 分半没装完（依赖链长，国内源拉不动）。
但真正需要的只有一个 176MB 的 u2net.onnx + onnxruntime（ComfyUI 早就有了）。
所以直接下模型、自己推理，跳过 rembg：
  下载  https://github.com/danielgatis/rembg/releases/download/v0.0.0/u2net.onnx
        （hf-mirror 那条路返回 429 限流，github release 4.8MB/s 直接过）
  推理  320x320 输入 -> 显著性图 d0 -> resize 回原尺寸
  效果  跳跃那张人物占比 16.8%，头发边缘、手指、裙摆、脚都抠得干净。

二 三段分区（这一步是关键）
----------------------------------------
只用"alpha > 0.5"二分，会在两件事之间二选一：
  - 阈值高了（0.5）：薄纱裙边、飘发被归进背景 -> 重绘时补出两只"透明翅膀"
  - 阈值低了（0.15）：原场景烘进人物边缘的光被归进人物 -> 留下一圈青色描边

所以分三段：
  >= 127   人物核心，绝不碰
  40~127   灰区（薄纱、飘发、边缘环境光），**保留像素但重新染色**
  < 40     纯背景，交给重绘（denoise 0.98）

重绘的 denoise 敢开到 0.98，和"人物区域重绘"完全相反：
背景不需要保留任何原信息，而且 mask 已经把人物挡在外面。

三 实测两组（同一套代码，差别只在原图的光）
----------------------------------------
  A 跳跃图（原图是青色霓虹夜雨，强逆光）
     樱花庭院：场景换得干净，但人物周围残留一圈青色轮廓光。
     这不是 mask 不准，是原图的光**烘进像素**了 —— 人物轮廓上那些青色
     本身就是画面内容。要根治得 relight（重打光），本地没这个能力。

  B 站姿图（原图是混凝土墙 + 中性白光）
     废弃教堂：彩窗、石柱、藤蔓、地面碎石、雾气全部到位，
     人物完整、边缘干净、光照也不冲突。**这张是能用的。**

  结论：背景层可用，但对原图光照有要求。
  想要干净的换背景，先出"中性光"的图（白光、平背景），再换场景。
  强氛围光（霓虹、逆光、魔法光）的图，换完必然带轮廓光。

为什么必须"画"：实测原图眼裂的亮度范围只有 27~130，
眼白正常要 220+，说明模型根本没画眼白，整个眼裂是一团灰蓝。
所以"分不清眼白和瞳孔"不是对比度不够，是这两个东西不存在。

做法（照画师四笔画）：
  1 rtmw 的 6 个眼裂关键点做凸包遮罩，绝不越界
  2 遮罩内铺眼白（取原图最亮中位数，提到 178）
  3 虹膜：正圆，半径 min(眼裂高x0.74, 眼裂宽x0.30)，
     圆心在眼裂 y+0.56 处 —— 下缘贴下眼睑，上缘被遮罩切掉
  4 虹膜色从原图采样，饱和度 x1.45（底模画的虹膜常常是灰的）
  5 瞳孔（虹膜x0.40）+ 左上高光点（虹膜x0.072）
  6 上眼睑投影压暗，让眼球陷进眼窝
  7 strength 0.65 混回，保留一点原纹理

踩过的坑：
  - 高光一开始画 0.20R，像个玻璃假眼，缩到 0.072 才自然
  - 虹膜初版圆心在眼裂中间，下半露大片眼白 = 翻白眼；
    挪到 y+0.56 后才贴合下眼睑
  - 这招只在"眼睛糊成一片"时用。原图眼睛已经清晰时合成是破坏，
    实测跳跃图（本来就是干净的蓝眼）被合成成一个灰盘子

============================================================
【颜文字当提示词】三条路都试了，结论是"得训"
============================================================
新增：kaomoji.py（渲染 + img2img + 可选 ControlNet）

一 文本路线：完全无效
----------------------------------------
SDXL 的文本编码器是 CLIP，词表 49408 个 token，以英文 BPE 为主。
颜文字的字符码位：
  (◕‿◕)  U+28 U+25D5 U+203F U+25D5 U+29
  ◉_◉    U+25C9 U+5F U+25C9
  T_T    U+54 U+5F U+54
"◕"(CIRCLE WITH ALL BUT UPPER LEFT QUADRANT BLACK)、"‿"(UNDERTIE)、
"◉"(FISHEYE) 都不在词表里，会被 byte-level fallback 拆成字节 token，
语义约等于噪声。而 "T_T" 更惨 —— T、_、T 都在词表里，
模型读到的是"字母 T 下划线 T"，和"哭"毫无关系。
所以不是效果差，是**没有信息进入模型**。

二 图像路线 A：img2img（denoise 0.88）
----------------------------------------
把颜文字渲染成 832x832 白底黑字（字撑满 80%），当初始 latent。
结果：四组（开心/哭/怒/面瘫）都出了清晰人脸，但**表情几乎一样**。
有趣的副产品：颜文字两侧的括号被模型画成了耳机 —— 说明图形确实被看见了，
只是它被当成"物体"而不是"表情"。denoise 0.88 又把这些形状信息冲掉了。

三 图像路线 B：+ ControlNet scribble（denoise 0.95）
----------------------------------------
结果更糟：中间的弧形被画成机械面罩/口罩，括号被画成天线和耳机。
四张表情仍然一致。

四 结论
----------------------------------------
模型没有"颜文字 = 表情"这个先验。它能看见这些形状，
但它对"圆圈 + 弧线"的解释是"耳机、面罩、天线"（赛博朋克物件），
不是"眼睛和嘴"。这不是调参能解决的 —— 需要训练。

可行的折中（没测，但方向明确）：
  颜文字当**眼睛/嘴的位置约束**，情绪交给提示词。
  即 (◕‿◕) + "smiling, happy, closed eyes"。
  但这时起作用的其实是提示词，颜文字只是陪衬。

真要实现你的设想，需要训一个"颜文字 -> 表情"的 LoRA：
把颜文字渲染成图和对应表情的人脸配对（几千对），
比 49 张图的画风 LoRA 更简单，因为配对数据可以程序生成。

============================================================
【多图参考】一条管角色、一条管服装、一条管质感、一条管动作
============================================================
新增：multi_ref.py

一 四张图走两条通道（这是核心）
----------------------------------------
  角色 / 服装 / 质感  ->  IP-Adapter 链（视觉特征注入 attention）
  动作                ->  ControlNet openpose（骨架约束空间结构）

  不能全用 IP-Adapter：它学的是"这张图长什么样"（长相、配色、笔触），
  就算 weight 拉到 0.9 也只能让画面"更接近参考图的构图"，
  不能指定"左腿抬 30 度"。姿势是空间约束，只有 ControlNet 管得了。
  也不能全用 ControlNet：它只管形状，管不了"这个角色的脸长什么样"。

  IP-Adapter 链做法：三个 IPAdapterAdvanced 串联，
  每个吃上一个输出的 model。weight_type 要分开：
      角色  linear          保留长相和轮廓
      服装  linear          保留款式和颜色分布
      质感  style transfer  只取笔触/配色，不抄构图

二 实测四种失败模式（都踩到了）
----------------------------------------
  1 会抄构图：参考图是低角度/跪姿，输出就低角度/跪姿，
    提示词里的 "full body, standing" 完全失效。
    -> 参考图必须和你要的构图接近，不能指望提示词纠正。

  2 多通道串联会稀释：三个都开 0.6 时，谁都不够强。
    实测 0.55/0.35/0.22 全部失效（角色被画成完全不同的发色）。

  3 **IP-Adapter 不能替代提示词**：DEFAULT_POS 里没写发色，
    模型就用了底模默认的蓝发，参考图是粉发也没用。
    正确配置：char 权重 0.80 + 提示词写明 "pink hair, short hair, blue eyes"
    -> 发色、服装、姿势全部到位。

  4 参考图内容会污染生成：用了一批带擦边倾向的参考图，
    输出直接跟着走（只穿上衣、低角度），负向加 nude/nsfw 也压不住。
    -> 选参考图等于选画风取向，含什么就会带什么。

三 可用配置（实测通过）
----------------------------------------
  python multi_ref.py --profile soft \
      --char ref_char.jpg            # 角色，权重 0.80
      --outfit ref_outfit.jpg        # 服装，权重 0.35
      --style ref_style.jpg          # 质感，权重 0.22，style transfer
      --pose pose_jump.png           # 动作，openpose 0.85，前 55% 生效
      --prompt "... pink hair, white sailor uniform ..."

  60 秒左右一张。角色、服装、动作三个维度可以分别指定，
  但前提是提示词把关键外观也写清楚，两者是配合关系，不是替代关系。

四 关于"AI 自己上网找参考图"
----------------------------------------
  技术上可行（搜索 + 下 + 直接喂），但有两个现实问题：
  1 版权：抓别人的图当参考生成，商用有风险
  2 质量不可控：搜到的图风格不统一，反而把画面带偏
  更稳的做法是维护自己的参考库（像现在 lora/inbox 那样），
  按"角色/服装/质感"分三个文件夹，用的时候从里面挑。

【纠正】上一轮的三个判断都不准，真因已经找到
============================================================
一 裸图是我的锅：提示词里漏了服装
----------------------------------------
multi_ref.py 的 DEFAULT_POS 原来只写：
    "pale skin, soft matte skin, delicate features"
—— 没写穿什么。模型自然自由发挥。
我上一轮把结果归因于"参考图污染"，判断错了。

修正后的写法（服装必须逐个部位写）：
    上衣  white sailor uniform, short sleeves, navy collar, blue bow, cropped top
    下装  white pleated skirt
    袜    white thighhighs
    鞋    white shoes
只写 "sailor uniform" 不够 —— 它只保证上衣，裙子得单独写，
否则模型自己决定给不给。

二 IP-Adapter 一直没生效：参考图不是正方形
----------------------------------------
ComfyUI 日志里写着：
    "the IPAdapter reference image is not a square,
     CLIPImageProcessor will resize and crop it at the center"
768x1344 的竖版全身图，**中心裁出来是躯干**，脸和服装全被切掉。
所以喂了粉发参考，出来是深蓝发 —— 不是权重不够，是图根本没进去。

修法：预处理时裁成正方形，焦点放在脸上（multi_ref.py 的 square_crop）。
修完之后粉发、水手服、蓝领结一次全部对上。

三 姿势跟不上：IP-Adapter 会压过 ControlNet
----------------------------------------
同一次运行里，全身构图（768x1344 + full body 提示词）回来了，
但骨架的单臂高举没跟上。openpose 0.85 / end 0.55 被 IP-Adapter 0.80 盖住。
想两者同时成立，骨架强度要提到 1.0、end 提到 0.7 以上。

============================================================
【合成流程改进】不再"抠了直接贴"
============================================================
新增：matte_composite.py

用户的原话是"像抠图贴在另一张画上，重点是还没扣干净"。
这个判断对，但问题在流程顺序，不在抠图算法：

  错的流程  复杂背景图 -> 抠 -> 贴
    原图的墙、霓虹、雾气会留在发丝和裙边里，永远抠不干净；
    人物身上带着原场景的光，贴到新场景必然不匹配；
    没有接触阴影，人是浮在地上的。

  对的流程  中性底图 -> 软alpha -> 去色溢 -> 合成 -> 接触阴影 -> 色温匹配
    1 出图时用**中性灰底**。不要绿幕 —— 实测绿幕权重 1.3 会把白上衣染绿
      （生成的那张水手服真的变绿了）；白底更糟，白裙会糊成一片。
    2 u2net 的软 alpha，不做二值化，发丝过渡全靠它
    3 despill：边缘像素里混进去的背景色成分减掉（绿边/白边都管）
    4 接触阴影：在人物最低点画模糊椭圆，人立刻落地
    5 色温匹配：按人物与背景的平均色比，只调 R/B 不动亮度

实测（绿幕源图 + 哥特教堂背景，768x1344）：
  边缘干净了、有阴影了、落地了。
  但人物整体还是偏亮 —— 根因在源图：绿幕强光下的白衣本来就过曝，
  任何后处理都救不回来。所以第 1 步（中性底 + 中间调光）才是关键。

【LoRA 能不能拆】先看数据，再谈技术
============================================================
ComfyUI 模型目录实际占用（69GB）：
    unet            23G    FLUX
    checkpoints     23G    4 个 SDXL 底模（Illustrious / WAI / Hassaku / MeinaV7）
    diffusers      6.5G    NOVA 3DCG
    text_encoders  4.8G
    controlnet     4.7G
    animatediff    2.5G
    clip_vision    2.4G
    ipadapter      1.4G
    vae            959M
    loras          129M   <- 只有这一个，134MB
  硬盘还剩 80GB。

  所以"拆 LoRA 省磁盘"这个动机不成立：LoRA 一共 129MB，
  拆到极致也就省一百多兆；而删一个 SDXL 底模能省 6.9GB，
  删 FLUX unet 能省 23GB。

关于"LoRA 之间有重复内容，能不能拆成组件再组装"：
  技术上能做三种拆法，但目的都不是省磁盘：
    按 block 拆   down/mid/up 分开，就是之前说质感 LoRA 的 block_dims 思路
    SVD 拆        把 ΔW=B·A 分解成主成分，能压秩（体积小 30-50%），但语义不可解释
    合并          两个 LoRA 同层权重相加 = 同时应用两个，不需要"拆"
  真正麻烦的是**冲突**：两个 LoRA 在同一层学到的方向相反时会互相抵消，
  常见解法是 TIES-Merging（先修剪小权重、按符号投票、再合并）。
  这是一套独立技术，值得做，但和"省磁盘"无关。

  另外：ComfyUI 里串两个 LoraLoader 就是"组装"，不需要物理合并。
  合并只在需要导出单文件给别人用时才有意义。

【骨架失灵的真正原因】不是强度，是提示词在跟骨架打架
============================================================
现象：multi_ref.py 同时挂 IP-Adapter（角色）和 openpose（骨架），
      构图、服装、发色都对，唯独姿势纹丝不动 —— 双手垂在身前站着，
      而骨架明明是"单臂高举 + 一手叉腰"。

第一轮怀疑：骨架强度不够，被 IP-Adapter 压过去了。
  改成 strength 0.85->1.0、end_percent 0.55->0.75，
  再让 IP-Adapter 提前收手（end_at 1.0->0.65），结果**姿势仍然不动**。
  从 ComfyUI history 里查到实际提交的图，参数确实生效了 —— 排除参数问题。

隔离实验（决定性）：
  A 只挂骨架、不挂参考图，提示词补上 "one arm raised up, hand on hip"
      -> 姿势完全正确
  B 骨架 + 参考图，同一句提示词
      -> 姿势同样正确，角色也锁住了
  结论：ControlNet 没坏，IP-Adapter 也不是元凶。
        元凶是 DEFAULT_POS 里只写了 "full body, standing"，
        **没有任何手臂描述**。文字在说"站着"，骨架在说"举手"，
        模型只能二选一，它选了文字。

规律（以后照这个配）：
  ControlNet 只约束形状，不改变文字条件。
  挂了骨架，提示词必须用同一方向描述姿势，否则等于让模型同时听两个指令。
  收紧 mask/提强度/延迟 IPA 都补不上这个缺口。

已加自动化：pose_hint() 按骨架文件名推断姿势词，
  含 jump  -> jumping, mid-air, arms up, knee up
  含 reach -> one arm raised up, arm up, other hand on hip
  含 sit   -> sitting, knees bent
  提示词里没有 "arm" 时自动追加，有则不动（不覆盖用户自己的描述）。

顺带修的两处：
  skeleton_gen.py 新增 --zoom，骨架整体缩小居中（0.86）。
    原因：骨架贴边时模型画的手臂更long，举手直接顶出画幅被裁掉。
    缩小后头顶和脚底都有余量，成品不再裁手裁脚。
  IP-Adapter end_at 默认 0.65：前 65% 建身份，后面交给提示词和骨架收尾。

============================================================
【合成流程 v3】"抠图贴上"的最后一层原因：源图自带投影
============================================================
上一版合成已经做了 despill / 接触阴影 / 色温匹配，但成品人物周围
仍有一圈深色轮廓。追下去发现根因不在合成，在**源图**：
模型出图时自己在人物身后画了一圈投影，像素值实测 RGB(1,0,1)、alpha 254，
也就是说 u2net 把它当成"不透明的人物"，跟着一起抠进了新场景。

两次失败的尝试（都记下来，避免再走）：
  1 抬 alpha 阈值（level 0.15）+ 过渡带判暗
     -> 暗边减轻，但残留。因为那圈影子 alpha 是 254，根本不在"过渡带"里。
  2 直接按亮度删暗像素（lum < 28）
     -> 影子没了，**五官线、裙褶线也一起没了**，整张图糊成一片。
        线稿和投影都是黑的，颜色上无法区分。

正确解法：靠拓扑区分，不靠颜色
  cut_uniform_bg() 四步：
    1 solid = 人物 且 非黑 且 非背景色       只剩实心色块
    2 solid 取最大连通块                      投影/反光这类孤立碎片自动丢弃
    3 填洞（floodFill 从边界灌）             被人物包住的黑色线稿重新归位
    4 solid × 原始 alpha + 轻度羽化           细发丝和软边保持原样
  实测面积 19.6% -> 15.9%，去掉的正是那圈投影，线稿完整保留。

配套修的接触阴影：
  原来椭圆画在 ys.max()（脚底那一行），大半在画面外，人看着悬空。
  现在中心上抬 0.8%H、右移 6% 身宽（跟着光的反方向），
  并叠一层更大更淡的环境遮蔽。两层叠起来才有"站在那儿"的感觉。

用法：
  python matte_composite.py --person 人物图 --bg-scene cherry --chroma
  --chroma 只在源图是**均匀单色底**时开（灰底、绿底都行）；
  源图本身是复杂场景时别开，会把场景当背景一起删。

最终效果（樱花庭院，768x1344）：
  深色轮廓消失、五官和裙褶线完整、脚下有接触阴影、边缘无绿边。
  仍然存在的差别是"光照不共享"——人物是正面平光，场景是斜射阳光，
  这一层要靠 relight（重打光）才能解决，本地没有这个能力。

============================================================
【本轮最重要的一条】IP-Adapter 会搬背景，不只是搬脸
============================================================
同一句提示词、同一个种子，只差挂不挂 IP-Adapter，量化对比：

  不挂            背景 std=0.3   背景色 (240,240,240)   轮廓环亮度比 1.000
  挂原始参考图     背景 std=25.2  背景色 (79,73,73)      轮廓环亮度比 0.252
  挂白底参考图     背景 std=0.5   背景色 (80,125,104)    轮廓环亮度比 1.005

  说明（指标含义）：
    std            背景区亮度标准差，越小越均匀
    轮廓环亮度比    人物轮廓外侧 4~14px 一圈的亮度 / 背景亮度
                   1.0 = 完全没有投影，0.25 = 一圈实打实的黑影

结论：IP-Adapter 把参考图的**背景、光向、投影**一起搬进画面。
你喂一张水泥墙硬光图，出来的就是水泥墙硬光图，而且人物身后带一圈黑投影
（实测像素 RGB(1,0,1)、alpha 254，所以 u2net 会把它当成"不透明的人物"）。

三组背景提示词对照（都不挂 IP-Adapter）：
  A 自然语言 "plain light gray background / solid seamless backdrop"  -> 纯白 std=0.3
  B Danbooru  "grey background, simple background, flat color background" -> 纯白 std=0.4
  C 标签加权  "(grey background:1.3) + 强压 shadow"                    -> 纯灰 std=0.6
  三个都干净。也就是说**背景本来就能压住，是 IP-Adapter 把它搅了**。

============================================================
【参考图怎么准备】不是越"干净"越好，抠图反而会教坏模型
============================================================
一 先修分割模型
----------------------------------------
u2net 是通用模型，遇到二次元图（床/沙发 + 柔和肤色）会把背景一起判成人物，
抠出来是一整块矩形。换成 isnetis（skytnt/anime-seg，1024 输入）后轮廓贴合。
  models/isnetis.onnx  167MB
  person_mask.alpha(src, model="isnet-anime")
两条坑（都是我自己挖的，记下来）：
  1 别改成"等比缩放 + 黑边 padding"。两个模型训练时都是把图压扁成正方形喂的
    （rembg 的 naive_cutout 就是 resize((320,320))）。改成 padding 之后，
    原本抠得很准的图从 16.8% 退化成 93%（整屏都是人）。
  2 min-max 归一化不能删。u2net 的 d0 原始输出不铺满 0~1，
    删掉之后同样退化成整屏 mask。
  另外 cv2.imread/imwrite 在 Windows 上读不了中文路径，matte_composite 里
  全部换成 np.fromfile + imdecode / imencode + tofile。

二 但白底"抠图"当参考会教出描边
----------------------------------------
用白底抠图（硬边 + 纯白）当 IP-Adapter 参考，出图会自带一圈"贴纸描边"
——背景干净了，但人物被一圈深色轮廓包着，合成后就是一圈绿边。

  白底抠图参考   人物占比 32.1%  （正常应该 20% 左右，多出来的是描边）
  白底自然渲染   人物占比 19.1%  （干净）
  抠图 + ipa_end 0.45   16.5%    （也干净）

所以两条可行路线：
  a 用"自然渲染 + 纯色底"的图当参考（不要抠图的那种硬边白底）
  b 照常用抠图参考，但把 IP-Adapter 的收手步提前到 0.45

============================================================
【新参数：IP-Adapter 要在 0.45 步收手】
============================================================
  ipa_end  1.00  身份最强，但背景/描边/构图全被搬，姿势也会被盖住
  ipa_end  0.65  背景干净了，人物周围仍留一圈描边（实测占比 32.1%）
  ipa_end  0.45  身份保住（白发蓝眼对得上），描边消失（16.5%）
  原理：前 45% 的步数把身份"烙"进 latent，之后交给提示词和骨架收尾，
        模型没机会再按参考图画一圈轮廓。
  已设为 multi_ref.py 的默认值。

============================================================
【一条命令跑完全流程】make.py
============================================================
  python make.py -c ref_0998187d2dca -P reach_up --scene cherry --upscale
                -p "white hair, long hair, blue eyes, white sailor uniform ..."

  -c  参考图：refs/char 里的名字 / input 里的文件名 / 任意图片路径（会现场裁切）
  -P  骨架预设：reach_up / jump / stand / sit（现场生成骨架，带 0.86 缩放的留白）
  -p  正向提示词（拼在默认主体描述后面）
      --scene cherry/ruin/night   换场景
      --upscale                   4x 超分
      --studio-only               只出影棚底

四阶段（实测一次 161.5 秒）：
  1 准备素材    骨架 0.2s + 参考图裁切
  2 生成        62.4s  768x1344
  3 4x 超分     20.1s  -> 3072x5376
  4 换场景      背景生成 28s + 合成 2s
产物统一在 output/make/<时间戳>/，文件名用 ASCII（01_shot / 02_upscaled / 03_scene），
因为 cv2 读不了中文名。跑完自动打开目录。

一个观察：挂了骨架 + IP-Adapter 之后，"grey background"这类背景提示词会失效，
出来的可能是绿色花纹墙。**但这不影响合成**——换背景时整块按 alpha 替换，
背景越花反而越好验证抠图是否干净（实测 19.4% -> 19.3%，说明 alpha 本来就准）。
只是这张图不适合直接当成品看。

遗留：举手类姿势（reach_up）的手仍可能贴到画幅上沿。已经用骨架 zoom 0.86 留过
余量，但 IP-Adapter 会把构图撑满，两者在争。彻底解决要给骨架再缩小或加大画布。

============================================================
【开关式工作流】每一段都能关，开关存在 toggles.json
============================================================
入口（三选一）：
  桌面「出图开关.bat」        双击，出现开关面板
  D:/AI-Video-Setup/8_出图开关.bat   同一个东西
  python switch.py            命令行版面板
  python make.py              不看面板，直接用 toggles.json 跑

面板长这样，输编号就翻：
  1  骨架        关（随机姿势）
  2  角色锁      开   [ref_0998187d2dca]
  3  4x 超分     开（+20 秒）
  4  换场景      关
  5  底模        3dcg
  6  尺寸        768x1344
  7  追加提示词  -
  c  换参考图（共 50 张可用）
  输编号翻开关    r = 立刻出图    q = 退出

骨架这一档有三种状态（这是本轮新加的）：
  off    不用 ControlNet。从 12 句姿势池里随机抽一句塞进提示词，
         模型自己发挥。出图约 40 秒，动作有区分度但不保证构图好看。
         （实测抽到"回头"那张容易出背面，已把这类姿势从池子里换掉）
  auto   随机抽一个骨架预设（reach_up / jump / stand / sit），
         带着结构约束随机。约 54 秒，动作多样且不会崩。
  指定   固定一个动作，每次都一样。要复现某张图就用这个 + 固定 seed。

姿势池（关骨架时用，12 句）：
  背手站立 / 双手抱胸 / 一手叉腰 / 走路 / 坐椅子翘腿 / 抱膝坐地
  / 靠墙屈腿 / 蹲下 / 伸展双臂 / 跑动 / 侧身站 / 踮脚
  每条可以带一句"反向词"，比如抽到坐姿就压 standing，避免模型两头听。

命令行等价写法：
  python make.py -P off         关骨架，随机姿势
  python make.py -P auto        随机骨架
  python make.py -P jump        指定跳跃
  python make.py -P off --no-upscale --no-char   只出草图（最快）
  python make.py -P auto --scene cherry --upscale -p "white hair, blue eyes"
  python make.py ... --save     把这次参数写回 toggles.json

另外 make.py 现在会自己检查 ComfyUI：没在跑就拉起来并等就绪（最多 180 秒），
不会只甩一串 connection refused 让人以为操作错了。

两个新的 .bat（8_出图开关.bat 和桌面的 出图开关.bat）都是
GBK + CRLF + 无 chcp —— 这是前面踩出来的规矩，UTF-8 + chcp 65001 会解析错行。


================================================================
十一、让 AI 自己找参考图（ref_search.py）
================================================================

你要的是"AI 觉得不好看能上网实时扒牛逼的参考图"。这条做了，
但先把现实摊开 —— 下面每个结论都是实测的，不是照抄教程。

  ---------------------------------------------------------------
  图源实测（2026-11-19，本机直连）
  ---------------------------------------------------------------
  danbooru.donmai.us     超时。国内直连无望。
  safebooru.donmai.us    403 + Cloudflare 挑战页，纯 HTTP 客户端过不去。
  konachan / yande.re    超时。
  e-shuushuu.net         404，响应还要 40 秒。
  www.zerochan.net       首页通，?json 一开始能出数据（带完整 tag 列表、
                         尺寸、md5，非常好用），但连续请求十几次后整个
                         搜索路径开始回 503，首页仍是 200 —— 反爬按路径封。
  safebooru.org          ★ 唯一能稳定用的。gelbooru 系 dapi，返回 XML。

  所以默认走 safebooru.org；Zerochan 和 danbooru 的实现都留着备用。
  你哪天挂了梯子，--site danbooru 是四个里面筛图最准的（它有 score 排序）。

  ---------------------------------------------------------------
  safebooru.org 是个什么站（这个必须知道）
  ---------------------------------------------------------------
  名字带 safe，本质是 gelbooru 的老镜像，分级字段是 gelbooru 的原始标记。
  抽 300 条 1girl：299 条是 q 级，1 条是 s 级。

  q 在 gelbooru 指"擦边"——泳装、内衣、轻度暴露，不是色情。
  但对创作参考仍然是污染：你要画正经角色，参考图却是泳装，
  服装和构图全带偏。所以默认只留 s 级。

  代价是量少。jumping 扫 900 条，s 级只有 6 张。
  放宽到 q（--allow-q）之后 300 条能出 26 张，质量也还过得去 ——
  动作和画风跟穿多少无关，这两类放宽是划算的；
  服装类别放宽，q 级的服装图多半就是泳装。

  还有个现实：这个站没有评分体系。danbooru 有 score 排序，好画师的作品
  会浮上来；safebooru.org 没有，所以垃圾比例很高。放宽 q 级之后实测
  下载的头 3 张，全是同人志封面（满版日文标题）、Q 版配 logo、卡片图。

  ---------------------------------------------------------------
  所以加了垃圾图过滤（JUNK_TAGS）
  ---------------------------------------------------------------
  带文字的一律不要：text / english_text / japanese_text / bilingual_text
    → 同人志封面、漫画截图、素材图
  分镜拼贴不要：comic / 4koma / multiple_views / split_screen / collage
    → 一格里塞好几个画面，裁方形必然切坏
  比例不对或不是成稿：chibi / artist_request / sketch / monochrome
  卡片杂志版式：card / trading_card / magazine_scan / scan / border

  实测：300 条 jumping，垃圾图过滤吃掉 251 条（83%），剩 26 张合格。
  下载 4 张看，2 张能用（跳姿全身、暗背景、无文字，很好），
  2 张不行（半身带白边 / 多人机车构图）。一半通过率。
  对"随手扒几张做参考"够了 —— 反正最后有图墙让你一眼挑。

  ---------------------------------------------------------------
  最大的坑：tag 之间是 AND，拼错一个词整条查询归零
  ---------------------------------------------------------------
  实测：
    jumping             20805 条
    jumping + solo       9787 条
    jumping + dynamic       0 条    ← dynamic 在这个站不是有效 tag

  糟糕的是它返回空列表、不报错。界面上看起来就是"没图"，
  你根本不知道自己写错了一个词。

  所以做了两级容错，顺序很关键：
    一级  直搜。绝大多数情况你写的词是对的，一次就中 —— 一次请求。
    二级  只有归零了才逐个单查、剔掉站上没有的词，然后贪心累加：
          从主词开始一个个往上加，加进去归零就跳过这个词。

  为什么贪心而不是"从后往前砍"：
    "jumping solo dynamic" 从后往前砍会先扔 solo，最后只剩 jumping，
    单人约束一起没了，回来一堆多人图。
    贪心则是 jumping → +solo（9787，留下）→ +dynamic（0，跳过），
    得到 "jumping solo"，正是想要的。

  最初的写法是每次都先跑一遍 tag 校验再搜，等于把请求预算花在大概率
  用不上的地方，还会把站打急（Zerochan 就是这么被打封的）。
  改成"先搜、失败才校验"，正常路径只要 1 个请求。

  ---------------------------------------------------------------
  用法
  ---------------------------------------------------------------
  双击  9_找参考图.bat（桌面也有 找参考图.bat），按提示选类别、输关键词。

  命令行：
    python ref_search.py --preset pose -q "jumping" -n 6 --allow-q
    python ref_search.py --preset scene -q "cherry blossoms, no humans" -n 5
    python ref_search.py --preset outfit -q "gothic lolita" -n 8
    python ref_search.py -q "white hair" --preset char -n 4 --dry   只看不下
    python ref_search.py --list-presets                            看各类规则
    python ref_search.py -q "..." --site danbooru                  挂梯子用，最准

  五个预设各自管什么：
    char    半身/头像，比例 0.55~1.70，加分 upper_body / portrait
    outfit  全身，比例 0.42~0.80，强制 solo
    pose    全身动作，比例 0.38~0.80，强制 solo
    style   不限方向，加分 highres / detailed
    scene   横幅，比例 1.10~2.40，强制 no_humans

  下载的是 600~850px 的样图，不是原图。IP-Adapter 用 CLIP ViT-H（输入 224），
  这个尺寸完全够；原图单张 4MB、实测 107KB/s，下 10 张要 6 分钟。
  真要拿去训 LoRA 才加 --size full。

  ---------------------------------------------------------------
  目录隔离（这条别搞错）
  ---------------------------------------------------------------
  refs/char/  是 prep_refs.py 产出的 49 张训练集 + 1 张自然底图，共 50 张。
              这是核心资产，别往里混网图，否则训练数据就脏了。

  所以网上扒的图存到 refs/<preset>_web/（char_web / pose_web ...）。
  交互向导里已经是这么写的；命令行手动 -c 时注意别写成 char。

  refs/_index.json 记着每张图的来源页、tag、下载时间。
  同一个 post 不会重复下载，下次搜到会自动跳过。

  ---------------------------------------------------------------
  什么时候别用它
  ---------------------------------------------------------------
  要"这个角色换个动作"：别扒图。角色长相你有 49 张精选图，
    动作直接 skeleton_gen.py 造骨架，比任何网图都准。
  要"某个特定场景"：matte_composite.py 里 SCENE_PROMPTS 那四套
    （cherry / ruin / night / studio）是本地生成的，可控、风格统一。
  要"稳定的画风"：等 LoRA 训出来，那个比喂参考图可靠。
  扒图真正的用武之地是：你不确定某种构图/服装/氛围长什么样，
    想先看几张实的再自己描述 —— 找灵感，不是当输入。


================================================================
十二、扒完图直接出图（ref_search → pack → make.py）
================================================================

上一章解决了"怎么扒图"。这一章解决"扒完怎么用" —— 手上有张动作照片，
可 pose 通道要的是 ControlNet 的骨架图，不是照片。中间缺的那一环补上了。

  ---------------------------------------------------------------
  链路
  ---------------------------------------------------------------
  python ref_search.py --preset pose -q "running" -n 3
      ↓ 下载图片
      ↓ 用 rtmw/Wholebody 从每张图里提取骨架（pose 类默认就做）
      ↓ 写一份 _pack.json，记着每张图的骨架、分数、来源
  python make.py --pack refs/pose_web
      ↓ 从包里挑分数最高、且提出骨架的那张
      ↓ 骨架按画幅装填，动作词自动补进提示词
      ↓ 出图

  想一次配齐：包里也记着 outfit / style 的图，multi_ref.py --pack 会把
  它们分到各自的通道（目录名 pose_web→pose，outfit_web→outfit …）。

  ---------------------------------------------------------------
  extract_pose.py 重写了，两个关键修正
  ---------------------------------------------------------------
  1 画在什么底上
    原来的写法是 draw_skeleton(img.copy(), ...) —— 直接把骨架画在原图上。
    原图的背景、衣服、头发全留着，等于给 ControlNet 喂"一张带人的照片"，
    它分不清哪条线是骨骼。现在先建纯黑画布再往上画。

  2 画几个点
    rtmlib 自带的 draw_skeleton 会把 wholebody 的 133 个点全画出来 ——
    光脸就 68 个，糊成一团白线（第一版成品就是这样，脑袋上顶着一坨）。
    SDXL 的 openpose 权重训练时只见过 18 个点，多出来那一百多个它不认识，
    反而把骨架读坏。现在从 COCO 17 点映射成 OpenPose 18 点再画，
    颈部用双肩中点补（检测器不输出颈点，缺了它头会飘在身体外面）。

  另外加了模型单例：Wholebody 初始化要几十秒，原来每张图重建一次，
  批量处理时全耗在加载上。现在 8 张图总共 10 秒左右。

  ---------------------------------------------------------------
  这一段是本次最费劲的排查，记下来省得重走
  ---------------------------------------------------------------
  症状：同一个骨架，-P jump 生效，--pack 死活不生效 ——
        喂的是"奔跑"骨架，出来是"靠墙站着扶头"，还不是崩坏，是"完全不听话"。

  依次排除了这些（全是错的方向）：
    × 以为是角色锁压过骨架 → 关掉 --no-char，一样不动
    × 以为是 IPA 权重太高 → 0.80 降到 0.60、ipa_end 0.45 提前到 0.35，一样
    × 以为是骨架尺寸不匹配 → fit_pose 等比装进 768x1344，一样
    × 以为是 workflow 没接上 → dump 两个工作的 ControlNet 节点，参数一模一样

  真正的验证方式：把提示词砍到只剩 "1girl, solo, full body, simple background"，
  同一个骨架立刻完美生效。**所以 ControlNet 从头到尾都是好的，是提示词在拖后腿。**

  一共三个词在捣鬼，全在 DEFAULT_POS 里：
    standing             和包里的动作词直接打架
    plain wall background 一有墙，模型就把"举臂抬腿"理解成"扶墙摆拍"
    looking at viewer     要求正面看镜头，模型为了满足它把身体拧成正脸摆拍，
                          奔跑这种有明确朝向的动作直接被掰回去

  pack 模式下这三个词会被自动压掉（背景反正后面要换掉，留着只会污染姿势）。
  教训：**姿势不对，先怀疑提示词和骨架互相打架，别急着调强度。**

  ---------------------------------------------------------------
  效果边界（这个要说清楚）
  ---------------------------------------------------------------
  坐姿：非常准。喂 sitting 的骨架，出来就是坐在箱子上、双腿并拢、手撑两侧。
  跑步：只能算"跟得上"。骨架的举臂、伸臂、腿的位置都对，但整体读起来
        更像摆拍 —— 因为网图骨架是从带透视的照片提的，refit 之后是斜的，
        模型会往"pose"方向理解。

  所以：
    要"准确的某个特定姿势"（坐/蹲/靠/抬手）→ 这个链路很好用
    要"跑跳翻滚这种动态大动作"          → 还是 skeleton_gen.py 手捏骨架更稳
    要"就是这张图的这个动作"            → 用这个，它是唯一能复刻的角度

  ---------------------------------------------------------------
  注意
  ---------------------------------------------------------------
  refs/pose_web/ 会越攒越多，_pack.json 只记最近一次扒的那批。
  想要前面扒的，直接 --pose 指定某个 skel_xxx.png 就行，文件都还在。

  pack 里的 char_web 会被拒绝：角色通道只认 refs/char 那 49 张精选图，
  网图是陌生人，锁不住你要画的人。


================================================================
十三、中文直搜：把"樱花树下奔跑的少女"翻成 tag（nl2tags.py）
================================================================

这是"聊胜于无"的一个功能，先说清楚它不是什么：
  它**不是**语言理解。没有接大模型，没有联网，就是一个 174 条的词典
  在做最长匹配。词表里有的能认出来，没有的就当没看见，句子结构完全不管。

为什么不上大模型：
  接 LLM 要 API key + 网络。而网络这块前面已经测得很清楚 ——
  扒 3 张图花 99 秒、SSL 握手超时、图站 503。为了一句翻译去赌网络，
  不如退一步用词典：失败了零成本，成功了省你打字。

  ---------------------------------------------------------------
  实测效果
  ---------------------------------------------------------------
  "少女在樱花树下奔跑"            →  running 1girl（加分：cherry_blossoms）
  "白发少女"                     →  1girl（加分：white_hair）
  "黑色大衣的少年"                →  1boy（加分：black_coat）
  "雨夜霓虹街道"                  →  night neon_lights（加分：street）
  "蹲下来看书的猫耳女孩"          →  crouching reading 1girl（加分：cat_ears）

  词表 174 条，分布：场景 36 / 服装 33 / 头发 27 / 动作 26 / 特效 13
  / 人物 12 / 眼睛 11 / 构图 10 / 颜色 6。

  ---------------------------------------------------------------
  最关键的设计：core 和 extra 分开
  ---------------------------------------------------------------
  一开始是直接把所有认出来的词都丢进查询，结果反而更差。
  因为图站是 AND：
    白发 + 跑步 + 1girl  →  大概率 0 条（跑步的人不一定会被标 white_hair）

  所以分成两组：
    core    只放"结构性"的词 —— 动作、人数、场景。这些词卡错了，
            出来的图完全不是要的那类，必须卡住。
    extra   颜色、发色、服装、特效。只参与**结果排序**，不进查询。
            这些特征本来就会由 IP-Adapter 从参考图带出来，
            没必要靠查询去卡，卡了只会把结果池子缩没。

  每种用途允许哪些类别进 core（nl2tags.CORE_CATS）：
    pose    动作 + 人数      —— 要的是姿势
    outfit  服装 + 人数      —— 要的是衣服
    char    人数 + 头发 + 眼睛 —— 要的是长相
    scene   场景 + 构图      —— 要的是环境
    style   只要人数

  这条规则是有代价换来的：早先"少女在樱花树下奔跑"会把
  cherry_blossoms 也塞进查询，52 条里最后只剩 6 条合格。

  ---------------------------------------------------------------
  另一个小设计：颜色和衣物要合成一个词
  ---------------------------------------------------------------
  "黑色大衣"如果拆成 black + coat，black 会单独进查询 ——
  而 black 在 safebooru 上是个极泛的 tag（黑背景、黑线稿都算），
  等于把查询稀释掉。所以相邻的 颜色 + 衣物/头发 会合并成
  black_coat、silver_long_hair、red_dress。

  ---------------------------------------------------------------
  开关（三种方式，任选）
  ---------------------------------------------------------------
  1  出图开关面板按 9            最方便，翻一下就存盘
  2  ref_search.py --no-nl       只对这一次生效
  3  toggles.json 里 nl_tags     改成 false 就是全局默认关

  关掉之后如果查询里还是中文，脚本会直接拦下并退出，
  不会拿中文去图站白跑一轮请求（实测中文 URL 只会 503 或空结果）。

  ---------------------------------------------------------------
  想加词
  ---------------------------------------------------------------
  打开 nl2tags.py 顶部的 DICT，照着这个格式加一行就行：
      "词": ("tag", "类别"),
  类别从 who / hair / eyes / cloth / color / action / scene / shot / effect 里选，
  它决定了这个词能不能进 core。加完直接生效，不用重启什么。

  优先级：长词自动优先（"过膝袜"不会被拆成"袜"），所以组合词放心加。


================================================================
十四、颜文字补测：地图路线走不通，查表路线直接可用
================================================================

前面"【颜文字当提示词】三条路都试了，结论是得训"那一章，
结论只对了一半 —— 那三条路（文本 / img2img / ControlNet）确实全废，
但"得训"这个判断下早了。第四条路不用训，而且效果立竿见影。

  ---------------------------------------------------------------
  先复盘前三条为什么全废（这部分结论不变）
  ---------------------------------------------------------------
  一  直接塞提示词       CLIP 词表 49408 个 token，没有 ◕ ‿ ◉ 这些字符，
                        会被 byte fallback 拆成字节，语义是噪声。
                        "T_T" 更冤 —— T、_、T 都在词表里，模型读到的是
                        "字母T下划线T"，跟哭毫无关系。
  二  img2img 起点       模型确实"看见"了形状，但把括号解释成耳机、
                        弧线解释成面罩 —— 它没有"颜文字=表情"的先验。
  三  + ControlNet       形状更硬，更糟：中间弧线直接成了机械口罩。

  卡点是同一件事：这三条都想让模型**照着形状画脸**。而模型不认识这种形状。

  ---------------------------------------------------------------
  第四条：不做形状，做语义
  ---------------------------------------------------------------
  颜文字真正携带的信息就两样：
    眼睛什么样（睁 / 闭 / 笑弯 / 含泪 / 星星）
    嘴什么样（闭 / 张 / 撇 / 大张）
  这两样用现成的表情 tag 就能精确表达，而模型对这些 tag 熟得不能再熟。

  所以：查表。42 个常见颜文字，每个映射到 3-5 个 danbooru 表情 tag。
  零训练、零显存、几十毫秒出结果。

  ---------------------------------------------------------------
  实测（同 seed 1111、同角色锁、同服装，只换颜文字）
  ---------------------------------------------------------------
    --kao "(╥﹏╥)"  →  crying, streaming tears, sad
        出来：眼睛含泪、眉头微蹙、嘴角下垂、脸颊有泪痕，坐姿缩着
    --kao "(≧▽≦)"  →  very happy, open mouth, laughing, ^_^
        出来：眼睛笑弯成 ^_^、张嘴大笑、双手举过头顶

  同一张脸，表情完全反转。这就是"颜文字当提示词"能用的形态。

  ---------------------------------------------------------------
  用法
  ---------------------------------------------------------------
  命令行（这是"独立输入框"，不跟普通提示词混）：
    python make.py --kao "(╥﹏╥)"                哭
    python make.py --kao "(๑•̀ㅂ•́)و✧"            坚定
    python make.py --kao "(◕‿◕)" -p "white hair"  颜文字 + 追加提示词

  面板：按 k 写颜文字，输入 ? 看支持哪 42 个，留空清掉。
  想关掉：面板按 k 再留空，或者把 toggles.json 的 kaomoji 设成 ""。

  只查表不出图：
    python kaomoji.py --tags "(◕‿◕)"

  ---------------------------------------------------------------
  两个实现细节
  ---------------------------------------------------------------
  1 表情 tag 插在提示词**最前面**
     SDXL 里靠前的词权重更高。表情是这张图的主题，
     写在后面会被服装、场景、姿势压掉。

  2 提示词里夹带的颜文字也认
     直接写在 -p "...(╥﹏╥)..." 里也行，会就地展开再挪到最前。
     兜底逻辑是"prompt 里出现码位大于 U+2000 的字符就试一次"。

  ---------------------------------------------------------------
  边界
  ---------------------------------------------------------------
  只认表里这 42 个。自己拼的、生僻的、纯符号的（比如 ╰(*°▽°*)╯）
  都可能不中，不中会提示并忽略，不会瞎猜。
  想加：改 kaomoji.py 顶部的 KAOMOJI_MAP，照着
      "(颜文字)": ["表情tag", ...],
  加一行就行，长词自动优先匹配。

  另外提醒：颜文字管的是**表情**，管不了脸型、年龄、画风。
  它替代不了角色参考图，两者是叠加关系。


================================================================
十五、开源：把仓库挪到别人机器上还能跑（paths.py）
================================================================

前面十四章都是"怎么出图"。这一章是"怎么让别人也能跑"。

  ---------------------------------------------------------------
  起因
  ---------------------------------------------------------------
  仓库推到 GitHub 之后做了一遍自查，发现两个问题：

  一  隐私：verify_style.py 里有三处写死的路径，指向本机的剪贴板临时图
      （C:/Users/<用户名>/.workbuddy/clipboard-images/...）。
      对别人毫无用处，公开出去也没意义。改成环境变量 REF_SRC，留空就跳过。

  二  移植：这才是致命的。17 处这样的写法：
        sys.path.insert(0, r"D:/AI-Video-Setup")
      仓库 clone 到 D:/code/comfyui-anime-lab 之后，这 17 个脚本
      第一行 import 就 ImportError。编译能过（语法没问题），
      运行时才炸。

  ---------------------------------------------------------------
  做法：把路径收进一处
  ---------------------------------------------------------------
  新增 paths.py：

    BASE   脚本所在目录，自动算（os.path.dirname(os.path.abspath(__file__))）
    COMFY  ComfyUI 根目录，按顺序探测：
             1  环境变量 COMFY_PATH
             2  仓库旁边的 ComfyUI_windows_portable\ComfyUI
             3  上一级目录的 ComfyUI
             4  D:/ComfyUI/ComfyUI_windows_portable/ComfyUI（作者环境）
             5  ~/ComfyUI、/opt/ComfyUI

  判断"是不是 ComfyUI 目录"用有没有 models 子目录，比认目录名可靠。

  于是移植从"改 20 个文件"变成"设一个变量"：
    set COMFY_PATH=E:/ComfyUI/ComfyUI_windows_portable/ComfyUI

  ---------------------------------------------------------------
  自动改代码踩的坑（这条比结论有用）
  ---------------------------------------------------------------
  这种替换是脚本批量做的，做完 py_compile 全过，看起来没问题。
  人工逐个看文件头才发现一处改错了：

    check_flux_clip.py 原本是
        sys.path.insert(0, r"D:/ComfyUI/.../ComfyUI")
    意图是**把 ComfyUI 自己的包加进 sys.path**（为了 import folder_paths）。
    机械替换成了 sys.path.insert(0, COMFY)，可那个文件里根本没有
    COMFY 这个名字 —— 而它又没有 import os，负责"补 import"的分支也没命中。

  编译不报错，运行才 NameError。**所以批量改完必须逐个看头部，
  不能拿"编译通过"当验收。**

  ---------------------------------------------------------------
  另一件事：README 别写不准确的话
  ---------------------------------------------------------------
  原来那张"移植"说明写着"每个脚本头部有两行常量 BASE / COMFY"。
  实际统计：43 个脚本里 14 个用 dirname、4 个硬编码 BASE、1 个才有 COMFY。
  照着改的人会找不到第二行，然后怀疑文档。

  现在改成实话：核心链路走 paths.py，设 COMFY_PATH 就行；
  test_*.py / diagnose_soft.py 那批是一次性调试快照，里面还留着
  当年的绝对路径和文件名，不保证开箱即用。

  ---------------------------------------------------------------
  推送方式（这台机器 git 协议不通）
  ---------------------------------------------------------------
  github.com 直连返回 502，api.github.com 是通的，所以走 Contents API：
  base64 传内容 + sha 覆盖。逐文件传完产生 22 条同名提交，太脏，
  于是用 git/commits 复用现有 tree、把 parent 指回根提交、再 force 移动
  ref —— 历史变成 2 条，**tree sha 前后一致**，一个字节都没动。

  校验办法（比看网页可靠）：git 的 blob sha 是内容的指纹，
    git hash-object --no-filters <file>      本地
    Contents API 返回的 .sha                   远程
  两者一致就说明服务器上存的字节和你本地完全相同。
  注意 Contents API **读**非 UTF-8 文件（比如 GBK 的 .bat）时会在输出层
  按 Latin-1 转码，看起来像乱码，但存储本身没问题 —— 用 blob sha 判断，
  别看显示。

  ---------------------------------------------------------------
  现在的边界
  ---------------------------------------------------------------
  能用：核心链路 8 个脚本 + 工作流 + 画风档，换机器设一个 COMFY_PATH。
  不能：模型权重、参考图、生成结果都不在仓库里（.gitignore 整目录排除），
        别人拿到的是"怎么搭"，不是"搭好的现成环境"。
